# Web-counter (Task 1) — Python

Веб-застосунок із лічильником (`/inc`, `/count`), клієнт-навантажувач, вимірювання
пропускної здатності (RPS) для лічильника **в пам'яті** і **на диску**, та Flame Graph.

**Усе, що потрібно для звіту, генерується кодом:** таблиці, CSV, порівняльний графік,
Flame Graph (PNG/SVG) і таблиці «які функції займають найбільше часу». Нічого не треба
рахувати чи малювати вручну.

---

## 0. Що вимагає завдання → де це в коді

| Вимога завдання | Де реалізовано |
|---|---|
| Веб-застосунок з `/inc` і `/count` | `app/server.py` |
| Багатопотоковість | `ThreadingHTTPServer` у `app/server.py` (потік на з'єднання) |
| Потокобезпечний лічильник, без lost-update | `app/counters.py`: `threading.Lock` (memory і disk) |
| Лічильник у файловій системі, гарантовано **на диску** | `DiskCounter` у `app/counters.py`: запис + `os.fsync` на кожен `/inc` |
| `/count` читає значення з диска | `DiskCounter.get()` читає файл |
| HTTP-клієнт, що міряє час | `tools/loadgen.py` |
| 1 / 2 / 5 / 10 клієнтів × 10K запитів, клієнти **одночасно** | `tools/loadgen.py` (процеси + `Barrier`), `tools/bench.py` |
| Перевірка кінцевого `count` (10K, 20K, 50K, 100K) | `loadgen` порівнює `/count` з очікуваним; `bench` ще й читає файл напряму |
| RPS = count / time | `tools/loadgen.py` |
| Порівняння in-memory і disk | `tools/report.py` (таблиця + графік) |
| Flame Graph для in-memory і disk при 10 × 10K | `tools/flame.py` (py-spy) |

## Етап 0. Ядро: розібратись і перевірити, що воно коректне

**Що тут є:** `app/counters.py` і `app/server.py`.

**Ключові ідеї (прочитайте коментарі в коді):**

1. **Lost update** — два потоки одночасно читають 5 і обидва записують 6 (мало бути 7).
   Запобігаємо `Lock`-ом: цикл «прочитати → +1 → записати» виконується по одному потоку.
   Навіть у Python з GIL `value += 1` **не атомарна**, тому замок потрібен і для лічильника в пам'яті.
2. **Гарантія запису на диск.** Звичайний `write` лишає дані в кеші ОС. Після кожного запису
   викликаємо `os.fsync()` — ОС зобов'язана скинути дані на диск. Це головна причина, чому
   disk-варіант повільніший.
3. **Багатопотоковість.** Звичайний `HTTPServer` обробляє запити по одному; ми беремо `ThreadingHTTPServer`.
4. **Keep-alive (`HTTP/1.1`) і `TCP_NODELAY`** — щоб міряти швидкість лічильника, а не встановлення
   з'єднань чи затримки алгоритму Нейґла.

**Запустіть:**

```bash
python -m unittest -v tests.test_counters     # усі тести мають бути OK
python -m tests.demo_lost_update              # наочна демонстрація
```

**На що дивитись:** тести — `OK`. У демо рядок `UnsafeDiskCounter` показує **втрачено > 0**
(код без замка губить оновлення), а `DiskCounter` — **втрачено = 0**.

**Ручна перевірка сервера** (два термінали):

```bash
# термінал 1
python -m app.server --mode memory
# термінал 2
curl http://127.0.0.1:8080/inc
curl http://127.0.0.1:8080/inc
curl http://127.0.0.1:8080/count      # -> 2   (приклад з умови завдання)
```
Зупинити сервер — `Ctrl+C`.

## Етап 1. Частина I — лічильник у пам'яті

**Що додається:** клієнт `tools/loadgen.py`, автоматизація `tools/bench.py`.

**Як працює клієнт:** кожен клієнт — окремий *процес* зі своїм keep-alive з'єднанням (процеси,
а не потоки — щоб сам клієнт не впирався в GIL). Усі клієнти підключаються, чекають на `Barrier`
і стартують **одночасно**; кожен робить 10 000 послідовних `/inc`. Потім читається `/count`
і порівнюється з `клієнтів × 10 000`.

**Запустіть:**

```bash
python stage1_inmemory.py            # повний прогін, як у завданні (~1 хв)
python stage1_inmemory.py --quick    # швидка перевірка працездатності
```

Скрипт сам запускає сервер, проганяє 1 → 2 → 5 → 10 клієнтів (по 3 повтори, береться медіана)
і зупиняє сервер.

**На що дивитись:**
* колонка `count` = `очікувалось` (10000, 20000, 50000, 100000) і позначка `OK` — немає lost update;
* `RPS` — це і є відповідь на «порахувати кількість запитів в секунду»; `avg`/`p99` — затримка запиту;
* як змінюється RPS зі зростанням кількості клієнтів (очікувано: спершу росте, потім виходить
  на плато — обмеження GIL та CPU машини, де сервер і клієнти працюють разом);
* файл `results/stage1_inmemory.csv` — усі замірі.

## Етап 2. Частина II — лічильник на диску + порівняння

**Що змінюється:** сервер запускається з `--mode disk`. Тепер `/inc` читає число з файлу,
додає 1, записує і робить `fsync`; `/count` читає з файлу. Змін у клієнті немає — міряємо те саме.

**Додатково перевіряється:** після кожного заміру число, що лежить у файлі `results/counter.dat`
(читається напряму, повз сервер), має дорівнювати очікуваному — доказ, що значення справді на диску.

**Запустіть** (після Етапу 1, щоб побудувалось порівняння):

```bash
python stage2_disk.py                # повний прогін (~4 хв — кожен запит чекає на fsync)
python stage2_disk.py --quick        # швидка перевірка
```

**На що дивитись:**
* ті самі колонки, що й в Етапі 1, плюс `OK` означає збіг і з `/count`, і з файлом;
* `results/comparison.txt` і **`results/comparison_rps.png`** — таблиця й графік «memory проти disk»;
* очікувана картина: disk повільніший, і **майже не масштабується** з кількістю клієнтів, а затримка
  зростає майже лінійно. Причина: `читання → запис → fsync` мусить виконуватись суворо по черзі
  (інакше — lost update), тож додаткові клієнти лише стають у чергу.

Це і є матеріал для розділу «Порівняйте та проаналізуйте результати».

## Етап 3. Частина III — Flame Graph

**Що додається:** `tools/flame.py` і `stage3_flamegraph.py`.

**Що робить скрипт для кожного режиму (автоматично):**
1. запускає сервер;
2. під'єднує **py-spy** — він 100 разів/с «фотографує», що виконує кожен потік сервера;
3. запускає **10 клієнтів × 10 000 запитів** (навантаження з завдання) і збирає профіль під час нього;
4. будує Flame Graph (PNG + SVG) і таблицю «які функції займають найбільше часу».

Для кожного режиму будуються два профілі (окремими прогонами):
* **`active`** — лише потоки, що виконуються (≈ CPU);
* **`wall`** — разом з очікуванням (замок, `fsync`, мережа). Без нього в disk-варіанті не видно головного.

```bash
python stage3_flamegraph.py                  # усе: 2 режими × 2 види (~3 хв)
python stage3_flamegraph.py --only disk      # лише один режим
python stage3_flamegraph.py --kind wall      # лише wall-clock профіль
python stage3_flamegraph.py --quick          # перевірка працездатності (мало семплів — відсотки неточні)
```

**Результат у `flamegraphs/`:** `wall_disk.png`, `wall_memory.png`, `active_disk.png`,
`active_memory.png` (+ `.svg`) — це і є «скріншоти Flame Graph» для звіту; `*_top.txt` — таблиці функцій
з відсотками; `*.folded` — дані, які можна відкрити на speedscope.app.

**Як читати Flame Graph:** знизу вгору — стек викликів («хто кого викликав»). **Ширина блока — частка часу.**
Широкий блок, над яким нічого немає, — місце, де час витрачається насправді.

**На що дивитись (очікувана картина):**
* **disk, wall** — майже вся ширина всередині `inc`, і майже все це **очікування замка** (власний час
  `inc`), поки один потік виконує `_write` (запис + `fsync`). Це видно й у `wall_disk_top.txt`
  (колонка «ВЛАСНИЙ ЧАС»). Висновок: вузьке місце — послідовний `fsync` під замком.
* **memory** — найширший блок — відправка відповіді по сокету (`write` у `socketserver.py`), а `inc`
  майже невидимий. Висновок: лічильник у пам'яті майже нічого не коштує, час іде на HTTP-обробку.

> `py-spy` не показує вкладених C-викликів (`os.fsync`, `lock.acquire`) окремим блоком: їхній час
> приписується Python-функції, що їх викликала. Тому `_write` = `pwrite + fsync`, а власний час `inc` =
> очікування замка.

## Як усе працює разом (одним абзацом)

`stage*.py` → `tools/bench.py` запускає **окремий процес** сервера (`python -m app.server`) → чекає,
поки він відповідає → `tools/loadgen.py` породжує N клієнтських процесів, які одночасно б'ють по
`/inc` → читається `/count` і звіряється → сервер зупиняється → результати пишуться в CSV, друкується таблиця.
Для Етапу 3 між запуском сервера і навантаженням підключається `py-spy`, а після — `tools/flame.py`
перетворює його дані на картинку.

## Типові проблеми

* **py-spy: `Permission denied` / `Operation not permitted`.** Профілювальник читає пам'ять процесу.
  Linux: запустіть `sudo -E env PATH="$PATH" python stage3_flamegraph.py` або один раз виконайте
  `sudo sysctl -w kernel.yama.ptrace_scope=0`. macOS: запускайте через `sudo`. У Docker додайте `--cap-add SYS_PTRACE`.
* **Windows.** Сервер, клієнт і Етапи 1–2 працюють, але Етап 3 (py-spy + SIGINT) надійно працює на Linux/macOS/WSL.
* **`Address already in use`.** Порт 8080 зайнятий — додайте `--port 8081` до команди етапу або зупиніть старий сервер.
* **Числа відрізняються від чужих.** RPS залежить від процесора й диска. Порівнюйте *співвідношення*
  (memory проти disk, зростання з клієнтами), а не абсолютні значення. Сервер і клієнти працюють на одній машині й ділять її ядра.
* **Експеримент без fsync.** `python -m app.server --mode disk --nofsync` показує, скільки коштує саме `fsync`,
  але **порушує гарантію запису на диск** — у вимірюваннях за завданням не використовується.
